# 데이터 사전 — 가상 데이터이지만 실제 인사 환경 구조를 그대로 따른다

> 원칙: 시연은 **가상 데이터**로만 한다. 하지만 표 구조·필드·출처는 실제 인사 시스템에서 내보낼 수 있는 형태로 만들어, 도입 시 **데이터만 바꿔 끼우면** 동작하게 한다.
> 생성: `node data/generate.mjs` → `data/*.json` (임직원 44명, 가상 계열사 8곳)

## 모든 행에 붙는 메타 필드
| 필드 | 뜻 |
|---|---|
| `_source` | 실제 환경에서 이 데이터가 오는 시스템 (HRIS, LMS, 성과관리 등) |
| `_tier` | 신뢰 등급: **시스템 확정 / 문서 근거 / 본인 기재 / 면담 확인 필요** — 화면에서 근거 옆에 표시 |
| `_note`, `_access` | 해석 주의점, 열람 권한 |

## 임직원 쪽 (평가 대상)
| 표 | 실제 출처 | 주요 필드 | 평가 축 | 등급 |
|---|---|---|---|---|
| `employees` | HRIS 인사 마스터 | 사번, 회사, 조직, 직무군·직무, 직급 밴드, 입사일 | 직무경험(근속) | 시스템 확정 |
| `appointments` | HRIS 발령 이력 | 기간, 조직, 직무, 발령 유형(입사·전보·**직무 전환**) | 직무경험(수행기간), 성장 가능성(직무 전환) | 시스템 확정 |
| `certifications` | 자격 등록 | 자격명, 발급기관, 취득일 | 업무 역량 | 시스템 확정 / 본인 기재 |
| `trainings` | LMS | 과정, 분류, 시간, 이수일 | 업무 역량, 성장 가능성(신규 역량 습득) | 시스템 확정 · *이수 ≠ 숙련* |
| `performance` | 성과관리 시스템 | 연도, 등급, **회사 내 상대 위치**, KPI 달성률, 평가자 코멘트 | 업무 성과 | 시스템 확정 · *열람 권한 필요* |
| `projects` | 프로젝트 시스템·경력기술서 | 목적, **본인 역할, 직접 수행, 수행하지 않은 범위**, 도구, 산출물, 근거 문서 | 직무경험(난이도·역할), 업무 역량, 업무 성과(기여도) | 문서 근거 / 본인 기재 |
| `evidence_docs` | 수행확인서 등 | 문서 ID, 종류, 발급일, 상태 | 모든 축의 근거 | 문서 근거 |
| `skills` | 스킬 인벤토리 | 기술, 수준(기초·실무·전문) | 업무 역량(숙련도) | 본인 기재 |
| `career_plans` | 경력개발계획(CDP) | 희망 직무, 장기 목표, **이동 의향** | 커리어 적합성 | 본인 기재 |
| `talent_pool_consents` | 그룹 인재풀 등록 | 동의 여부, 범위, 유효기간 | **스캔 대상 여부** | — |
| `availability` | 본인·소속 조직 입력 | 시작 가능일, 최대 투입률, 조직 협의 상태 | 적합성과 분리된 **이동 가능성** | 본인 기재 / 면담 확인 필요 |

## 직무 쪽 (판단 기준)
| 표 | 실제 출처 | 주요 필드 | 쓰임 |
|---|---|---|---|
| `jobs` | 공모 시스템·현업 요청서 | 업무, 필수·우대, 기간·투입률·근무지·직급 범위(하드 필터), **성공 기준, 팀에 부족한 역량** | 요건 분해의 입력 |
| `job_standards` | NCS 형식 직무 표준 | 능력단위별 지식·기술·태도 | 정성 요건의 근거 ("학술 자료" 구체화) · *시연용 요약이며 실제 NCS 원문 아님* |
| `high_performer_patterns` | 인사 시스템 익명 집계 | 표본 수, **최소 표본 규칙(10명)**, 공통 경험 비율 | 우대 요건·가중치 근거 |
| `predecessor_notes` | 현업 인터뷰 메모 | 자유 텍스트(개인 식별 정보 제외) | 실제 병목 파악 |
| `skill_synonyms` | 인사팀 관리 사전 | 표준 역량 ↔ 다른 표현들 | 표현이 달라도 같은 경험 연결 |

## 기존 스키마에서 바꾼 점
| 기존 | 변경 | 이유 |
|---|---|---|
| 성과 등급을 그대로 비교 | **회사 내 상대 위치** 함께 저장, 계열사 간엔 상대 위치만 사용 | 계열사마다 KPI 난이도·등급 분포가 다름 |
| 학습 민첩성 · 도전 의지 (정성) | **직무 전환 이력, 최근 신규 역량 습득, 자원 참여 과제**(관찰 가능한 행동)로 대체, 나머지는 면담 확인 | 측정 데이터가 없고 성향 추론 위험 |
| 지원 동기 | 지원자만 보유, 숨은 후보는 "면담 시 확인" | 미지원자에게는 없는 데이터 |
| (없음) | `talent_pool_consents` 추가 | 계열사는 별도 법인 → 계열사 간 인사 정보 활용에 본인 동의 필요 |
| (없음) | `availability` 분리 | "적합한 경험"과 "실제 이동 가능"을 따로 판단 |
| (없음) | `jobs.success_criteria`, `team_gap` | JD만으로는 성공 기준을 알 수 없음 |

## 평가에서 쓰지 않는 것
성별, 나이, 출신 학교·지역, 가족 관계 등 직무 수행과 직접 관련 없는 속성은 **만들지도, 입력하지도 않는다.**

## 남은 정리
- 화면(`hr_matching.html`, `employee.html`)은 아직 페이지 안에 적은 데이터를 쓴다. Supabase를 연결할 때 이 `data/*.json`을 DB에 넣고 화면이 그걸 읽도록 바꾼다.
- 상세 인물 4명(김서윤·이한결·박지호·최예린)은 화면과 사실이 같다. 화면의 정민호·한다인·오태경·윤채원은 여기서는 생성 데이터라 DB 연결 시 맞춘다.
